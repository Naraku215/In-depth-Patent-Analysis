# 专利解剖台

解剖台不是“把专利做成一台漂亮的三维模型”，而是用可操作的空间关系回答读者的问题：这台东西由什么组成、气流/物料怎么走、哪一段承担什么任务。

## 先定讲解，再定几何

先写清三件事，再动 `scenes.js`：

1. **一句话主线**：这件专利最核心的因果是什么？
2. **读图顺序**：读者应该先看哪一段，再看哪一段？
3. **每个视图的问题**：这个视图只回答哪一个问题？

视图数量由材料决定，不固定 1 个、3 个或 5 个。一个视图能讲清就不要拆；需要放大、剖切、对照时再加。不要为了“看起来完整”添加专利没有的装饰件。

## 读图优先级

形状来自两处：**文字描述**和**专利附图**。附图通常更准，尤其是连接关系、剖面和标号位置。

从阶段 1 的「读图记录」里取：

- 哪张图最适合回答第一个问题；
- 标号在图上落在哪个零件、哪一侧、哪一段；
- 哪些尺寸是原文实测/清单值，哪些只是为了可读性补的示意；
- 同一标号在不同图中是否有不同含义。

图里画了、文字也支持的结构要建；为了可读性补的支座、接管、断长或剖切，必须在 `notes`/`caption` 里标明“示意”。示意件不能占据画面主体。

## scenes.js：几何与标签

### 场景注册

```js
A.scenes.p1 = {
  id: 'p1',
  code: 'US 10,150,093 B2',
  short: '微结构反应器 · 蒸发冷却',
  patentee: 'INERATEC / KIT · 2018 授权',
  tag: '装置',
  views: [
    { id: 'stack', label: '叠层解剖', build: viewStack },
    { id: 'field', label: '冷却场', build: viewField },
  ]
};
```

### 可用的绘图调用

| 调用 | 作用 |
|---|---|
| `b.group(name, {explode:[dx,dy,dz]})` | 注册可爆炸组；位移量只影响演示，不影响事实 |
| `b.box(...)` | 轴对齐长方体 |
| `b.line(...)` | 折线/中心线/流线 |
| `b.tube(...)` | 管线 |
| `b.label([x,y,z], '21 部件名', {color,dx,dy,anchor,group})` | 标号与引线 |
| `b.flow(path, {count,speed,color})` | 流动粒子；颜色和速度是讲解手段，不是实测 |
| `return done(b, {view:{yaw,pitch,zoom}})` | 收尾 |

坐标：`+x` 右、`+y` 里、`+z` 上。模型尺寸不必等于真实比例，但不能把关键拓扑关系画反。

### 视图设计

- 先用侧视、半剖或轴测把主流程讲清，再决定是否需要旋转和爆炸。
- 每个视图的标签数量由信息密度决定，不设固定上限；但只标当前视图真正要讲的部件。
- 标号必须锚在实际零件上，不能落在空白、支座或背景上。
- 同一个数字在不同图中有不同含义时，标签和右栏表都要写出图号，例如 `25 冷却液出口（图1）`、`25 后级补气（图9）`。
- 3D 视图可以有 `explode`/`flow`，但纯流程示意或对比视图不必为了“动起来”硬加动画。

## report.js：讲解与标号

```js
A.patents.p1 = {
  title: '…',            // ≤ 30 字
  abstract: '…',         // 讲清问题、解法、代价
  facts: [['申请人','…'], ['授权','…'], ['权项','N 项']],
  claim: '权项 1 的要害…'
};

A.notes['p1:stack'] = {
  key: '图1 / 图2',
  title: '…',
  body: ['一句话主线…'],
  steps: ['先看…', '再看…', '最后…'], // 可选，推荐用于流程/结构关系
  after: '最容易误读的一点…',          // 可选
  parts: [
    ['21', '等离子炬', '最左端铜色体'], // 第三个位置提示可选
    ['25', '冷却液出口（图1）']
  ],
  tags: ['结构有据', '示意项已标注']
};
```

讲解不需要套固定段落模板。可以用连续段落、步骤、对照表或误读提示，但必须让读者知道：

- 这台东西在解决什么问题；
- 气流/物料/能量按什么顺序走；
- 每个关键标号在画面哪里、承担什么任务；
- 哪些是专利明说的，哪些是模型示意。

## 标号纪律

`parts` 里每个编号必须能在 `facts.numerals` 或 `facts.referenceSigns` 里找到来源。

美国专利常用 `a plasma torch 21` 这种“名词 + 数字”写法。优先看：

- `facts.numerals`：清单/显式内联标号；
- `facts.referenceSigns`：名词后缀候选，带有原文行号和上下文；
- `facts.figureSigns`：按图号分组的候选。

候选不是自动真值。必须结合附图确认“这个数字到底指哪个零件”。如果同一数字在不同图中含义不同，必须带图号区分。

## 自动语义验收

`verify` 和 `package` 会检查：

- 每个 3D 视图里的数字标签，与右栏 `parts` 表是否一一对应；
- 标签是否跑出视口；
- 标签是否严重重叠；
- 页面是否有 console error。

这些检查只约束“语义自洽”，不限制视图数量、画法、配色、叙述顺序或标签位置。不要为了通过检查把模型做成固定模板。

## 验收

```bash
node bin/patent.mjs build <id>
node bin/patent.mjs verify <id>
node bin/patent.mjs package <id>
```

`verify` 里 `语义 station` 应为 `ok`；`label-outside-viewport` 和 `label-overlap` 会作为建议提示，不阻断交付。标签与右栏表不一致会阻断 `package`。
